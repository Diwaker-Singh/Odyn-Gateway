# Runbook: throttling responses

1. Compare aggregate 429 responses with the configured per-principal/global
   rate and budget limits.
2. Confirm responses include a valid integer `Retry-After` and clients back off
   instead of retrying in a tight loop.
3. Check shared-store health, admission latency and conditional-write conflicts.
   Distinguish intentional rejection from storage failures reported as 503.
4. If a client is looping or the store is unhealthy, reduce or pause its
   traffic. Do not relax admission limits during an incident without reviewing
   the capacity and cost impact.
5. After mitigation, verify a valid request succeeds and rejected requests
   still receive bounded retry guidance.
